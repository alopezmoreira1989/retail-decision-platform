# Development Guide

## Fictional data statement

All company names, retailers, brands, products, store data, and personal names used or generated by this project are **fictional and synthetically produced**. Retailer archetypes are inspired by patterns that are common knowledge in the retail analytics industry (e.g. "some retailers send daily POS, some send weekly aggregates"), not by any specific real company's implementation. This project does not reproduce, copy, or expose proprietary business logic, data, thresholds, or architecture belonging to any employer, client, or third party.

## Branching strategy

- **`main`** — the stable/"production" branch. Always deployable/demoable. Direct commits are avoided; changes land via pull request from `dev`.
- **`dev`** — the integration branch. Day-to-day feature work targets `dev` via short-lived feature branches (`feature/<short-description>`), merged via PR.
- Periodically, once `dev` is in a stable, demonstrable state, it is merged into `main` (tagged as a milestone checkpoint where useful).
- Hotfixes to `main` (rare, e.g. fixing a broken README) may be branched directly from `main` and merged back into both `main` and `dev`.

```text
feature/xyz ──PR──▶ dev ──periodic PR──▶ main
```

## Repository conventions

- **Python** ≥ 3.11, dependency and tool configuration centralized in `pyproject.toml`.
- **Formatting/linting**: `ruff` (lint) and `ruff format` (format), enforced via `pre-commit` and CI. Configuration lives in `pyproject.toml`.
- **Pre-commit hooks**: install once with `pre-commit install`; hooks run automatically on `git commit` and also run in CI to prevent drift.
- **Tests**: `pytest`, under `tests/`, mirroring the top-level package layout. Unit tests for simulator/model logic; separate evaluation-style tests that compare against hidden ground truth live behind an explicit "evaluation" marker so they're not confused with unit correctness tests.
- **Commit messages**: short imperative summary line (e.g. `Add store generator`), body explaining *why* when the reasoning isn't obvious from the diff.
- **No premature abstraction**: modules are added when a milestone needs them, not speculatively. Config-driven variation (e.g. retailer differences) is preferred over branching code paths.

## Local environment

The project targets a fully local, low-infrastructure development loop:

- **DuckDB** as the local analytical engine — no database server required.
- **Parquet** on local disk (or a mounted volume) as the storage layer for Bronze/Silver/Gold.
- **dbt Core** (`transformations/`) run locally against DuckDB.
- **Docker / Docker Compose** (`infrastructure/`, from Milestone 9) for orchestrated, reproducible runs (e.g. Airflow), not required for early-milestone development.

Setup steps will be added here as the environment is established in Milestone 1 (see the corresponding issue), so that `pip install -e .[dev]` (or equivalent) plus `pre-commit install` is enough to start contributing.

## Testing philosophy

Three layers are expected to emerge as the project develops:

1. **Unit tests** — deterministic checks of individual functions/modules (e.g. "the identifier resolver maps a known alias correctly").
2. **Pipeline/integration tests** — a small end-to-end run (simulator → RAW → Silver → Gold → one model → one recommendation) executed against a fixed seed, checked for structural correctness.
3. **Evaluation experiments** — offline comparisons against hidden ground truth (e.g. precision/recall of a detection model under varying data quality), reported rather than pass/fail asserted. These live separately from CI-blocking tests since they're experiments, not correctness gates.

## CI

GitHub Actions runs lint (`ruff check`), format check (`ruff format --check`), and `pytest` on every pull request. The workflow is intentionally minimal at project start and grows alongside the codebase (see Milestone 9 for orchestration-grade CI/CD: dbt build checks, containerized runs, etc.).

## Working on issues

Each GitHub issue is scoped to be implementable independently, includes an objective, context, proposed approach, and acceptance criteria, and is assigned to a milestone. Check an issue's "Dependencies" note (if present) before starting — some are ordered.
